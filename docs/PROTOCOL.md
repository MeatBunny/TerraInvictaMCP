# TerraInvictaMCP wire protocol (in-game DLL)

Unity Mod Manager (UMM) loads this DLL mod. The mod uses Harmony to patch
game methods at runtime. It runs a localhost TCP server, the bridge, inside
Terra Invicta. External tools such as AI agents or scripts speak the protocol:
Claude Code, OpenCode, Antigravity, or plain netcat. They can drive a running
campaign, issue commands, read game state as JSON, and control time without
the GUI. A verb is one named request that the bridge answers.

This document describes the contract shipped with mod version 0.1.0. Verbs
added after that carry a "since <version>" note on their row.

## Design principles

- **Thin DLL.** The mod exposes simple verbs. Sequencing, judgment, and test
  logic live in the client scripts. A DLL change requires a game restart. A script
  change costs nothing.
- **Never crash the game.** Every command runs inside a catch-all block. Failures
  return an error response. A broken bridge becomes an inert mod. One verb is
  an exception, because its whole purpose is to crash the game:
  `test.crash_the_game` is a test fixture for the crash flag below. It runs inside the
  same catch-all as every other verb and never throws. It puts the game into its
  crash state and answers normally over it. It refuses to run without an explicit
  confirmation argument.
- **Grow on demand.** A new verb enters the mod only when the existing verbs
  cannot do a task. Unknown commands return an error. Clients can
  feature-detect against `version`.

## Transport and protocol

- TCP on `127.0.0.1:17470`. The bridge listens on localhost only and has no
  auth. Anything on this machine already has the same user privileges. If the
  bind fails, the mod logs one line and runs inert.
- Newline-delimited JSON (NDJSON: one JSON object per line), UTF-8. Request: `{"id": <int>, "cmd": "<verb>",
  "args": {...}}`. Response: `{"id": <int>, "ok": true, "data": ...}` or
  `{"id": <int>, "ok": false, "error": "<message>"}`.
- Since 0.1.1 every response envelope, success and error, also carries three
  keys:
  - **`clockStall`**: seconds that the game went without gaining time, or null
    when there is nothing to measure (no campaign, or no frame yet since one
    loaded). A per-frame watchdog measures it against
    `Time.realtimeSinceStartup` and restarts when a campaign loads. Two
    conditions count as a stall: a clock that does not move, and a clock that
    crawls (speed index below 3 with no `run_until` armed). Each time the
    current stall passes another whole five minutes (5, 10, 15), the DLL
    writes one line through the UMM logger (Player.log,
    `log_tail which=player`): `[TerraInvictaMCP] clock stalled N s, state=<state>,
    prompt=<blocking prompt or none>, last verb <M> s ago`. It writes the line
    only after some client executed a verb in this session.
  - **`campaignToken`**: a string that names the loaded campaign, or null. It
    changes on every transition into a campaign, verb-ordered or not, and
    never otherwise. The DLL mints it (a counter behind a per-process prefix)
    because `GameStateManager.ClearAllGameStates` restarts the state-id
    allocator. As a result, a second campaign of one scenario reuses every id.
  - **`campaignProcess`**: the token's prefix on a key of its own. The DLL takes
    it once at mod load. It is a string on every reply, with or without a
    campaign. It names the game process that answers, because the token's
    counter restarts at 1 in each process.
- The bridge accepts multiple concurrent connections. All commands funnel into one
  FIFO queue. Each connection gets responses in the order that it sent requests.
- `version` reports the mod version as `mod`.

## Execution model

- A background thread owns the socket to accept, read lines, and enqueue.
- Commands run on the main thread from the UMM `OnUpdate` callback. This
  survives scene reloads and save loads. The queue drains once per frame.
- Verbs must complete within a frame. A verb starts each long-running task.
  A per-frame tick advances the task, and the client observes it by polling
  (see `time.run_until` and `combat.autoresolve`).
- With no campaign loaded, game verbs return `error: "no campaign"`. The verbs `ping`
  and `version` always work.
- The bridge outlives a crash in game code. A client must read the crash flag
  and must not infer a dead game from a frozen clock. `GlobalInstaller.HandleException`
  sets `GameControl.handlingException`, shows the crash panel, calls `PauseAndBlock`,
  clears every event listener and turns input off. The mod's update runs off the mod
  loader's own MonoBehaviour. So every verb keeps answering through the crash state,
  and the blocked clock reads exactly like a modal alert. `query.time.crashed` and
  `version.crashed` report the flag. Recovery is a process restart. The flag has one
  writer in the assembly and no clearer, and it survives a scene load. So a save
  loaded into the same process comes back with the Escape key dead, and two combat
  controllers return immediately from their per-frame methods. `test.crash_the_game`
  puts the game into exactly that state on demand. So a client can test its handling
  of that state without waiting for a real crash.
- **The clock must not be handed back into an open councilor mission phase.**
  A semimonthly tick that lands inside an open phase corrupts the phase state.
  So a driver that holds a phase issues no `time.speed` and no `time.play`. It
  pauses a running clock, and it hands the clock back once `query.time` reports
  the phase closed. `time.run_until` refuses a new target while a phase is open
  (`force: true` overrides). Under an `ai.control` engagement, the engagement
  defers the colliding tick instead. See the `query.time`, `time.run_until` and
  `ai.control` rows.

## Arguments

**Argument types are taken literally.** A verb that wants an integer takes the
JSON integer token and nothing else. It refuses `2.5` and does not round it,
and it also refuses `true` and `"2"`. A verb that wants a number takes an
integer or a float, and never a string. So a thousands separator or a decimal
comma cannot arrive as a number that nobody asked for. The refusal names the
argument and the token type that it got:

```
arg 'slot' must be an integer, got Float
arg 'strength' must be a number, got String
```

A whole number of the right type but the wrong size answers `arg '<key>' is out
of range for a 32-bit integer`. An argument that takes a number has no such
refusal. An integer literal that is too large to convert saturates to an
infinity. The finiteness test that keeps NaN and the infinities out of campaign
state catches it as `arg '<key>' must be a finite number`.

Every tool in the MCP table declares these arguments as `integer` or `number`.
So a client that checks its calls against the schema never sends anything
else. The refusal exists for a hand-written `raw` or `batch` call.

| `query.state` | `id` XOR `root`, `path?`, `include_private?`, `fields?`, `limit?` | reflection dump at depth 1 of whatever the arguments land on. Start from exactly one of `id` (a registered game state) or `root` (a static entry point, `TypeName.Member[.Member...]`). The type of a root resolves against Assembly-CSharp, then `PavonisInteractive.TerraInvicta`, then every loaded assembly. The longest prefix that resolves to a type wins. `path` then walks from there. It is identifier segments separated by dots. Each segment has at most one `[n]` integer indexer, applied to an `IList` or array (`player.aiValues`, `currentSpeeds[2].displayName`). Dictionary keys are not addressable. The walk tries fields before properties. A property getter runs game code, and a getter that mutates is the caller's risk. A step that fails answers an error that names the segment and the type that it failed on (`no member 'aiValues' on TIPlayerState at segment 2`). It never answers a silent null. **`include_private`** (default false) adds non-public instance members to both member lookup and the endpoint dump. **Endpoint:** a game state answers `{id, type, name, members}`. A value that the dump renders whole (string, enum, number, bool, date, template as its `dataName`, or an expandable list) answers `{type, value}`. **Since 0.1.1, a `Dictionary<K,V>` that the walk lands on answers `{type, value}` too**, if both its type arguments are expandable. The value is a JSON object keyed by the rendered key (a template key as its `dataName`, an enum key by name, a game-state key as `name (id)`). When two keys render alike, the value is an array of `{key, value}` pairs instead, with `duplicateKey: true` on each repeated key. A client reads `TIFactionState.objectives` and `objectiveNames` (both private: `path=objectives include_private=true`) and `TIControlPoint.controlPointPriorities` this way. **This applies at the endpoint only.** Walk onto the dictionary with `path`. In a member dump, a dictionary stays a bare type name, as a nested list does. Anything else answers `{type, members}`. Every response echoes `root` and `path`. **Members:** the dump gives scalars verbatim and collapses game-state refs to `{id, type, name}`. A list or single-dimension array expands when its declared element type is a game state, a template (each its `dataName`), a string, a char, an enum (by name), or a number or bool. **Caps:** `path` and `root` each take at most 16 dot-separated parts, and the verb refuses more on the split. An expanded list or dictionary cuts at 200 entries, and an expanded dictionary also at 65536 characters. The dump always renders the first pair, whatever its size. **At the endpoint, the reply reports the cut:** `valueCount` (the collection's own count, null when it does not report one), `valueShown`, `valueTruncated` and `valueTruncatedBy` (`entries`, `characters`, or null). So "key K is absent" past the cap is not a silent false negative. A dictionary also carries `valueShape` (`object` or `pairs`). It does so because the same path can answer an object on one call and pairs on the next. Inside a member dump, a list still cuts with no marker. **Member selection and paging:** members come out in ordinal name order. A member endpoint carries `count` (the members that the filters left), `returned` and `truncated` beside the dump. **`fields`** is an allowlist of member names (at most 32, matched case-insensitively like a path segment). The verb applies it before `limit`. The requested names that matched nothing come back as `missingFields`. A value or collection endpoint has no members to filter, so `fields` there is an error rather than an empty dump. **`limit`** caps how many members the verb reads, so it also caps the getters that run. It must be at least 1. If it is absent, the verb reads every member. Like `fields`, it is an error on a value or collection endpoint. |

## Ship designs

`design.create`, `design.delete` and `design.auto` cover a surface nothing else
in the bridge reaches. A ship design is a `TISpaceShipTemplate` built at run
time and registered with `TemplateManager`, and the only way a player makes one
is the ship designer: a hull picker, a drive picker and a slot grid, all mouse.
For a driving agent the UI is view-only, so before these verbs the designs a
test could use were the designs the campaign happened to ship with, and the
question "does this mod's laser fit on a vanilla hull" had no headless answer.

`design.create` is the by-hand path and takes every part by name. It is not a
fixture in the `spawn.*` sense. It enforces the engine's own validity rules.
With `legal`, it also enforces the engine's own research gate. So a refusal is a
real answer about the parts and not a limit of the harness. `legal: false` is
the fixture, and it says so.

`design.auto` is the engine's own search. `spawn.fleet` is the other half of
both `design.create` and `design.auto`. A design proves that the parts go

## Mod inspection

Templates and both mod loaders finish at boot. The mod verbs (`mods.list`,
`query.template`, `query.enums` and `harmony.patches`) answer with no campaign
loaded.

For `mods.list`, DLL mods come from `UnityModManager.modEntries`. Template mods come
from the game's own records. `mods.list` reads these records and never rebuilds them.
`ModManager.ModNames` / `DisabledModNames` are for the folders the loader accepted.
`ModTemplateManager.jsonMods` is for the individual JSON files it merged. Each carries
its load order, its target vanilla file, the data names it touches, and whether it
matched a vanilla template at all. A file that matched nothing is the shape that crashes
template load. `TIPlayerProfileManager.useMods` is the `use mods` checkbox. With it off,
the game ignores JSON and localization mods outright. The verbs also report the folder
listing from `Mods/Enabled` and `Mods/Disabled`, so that you can compare what the loader
saw with what is on disk.

`query.template` reaches templates through `TemplateManager.GetAllTemplates<T>`. This
is bound at runtime to the class named by `type`. The name is resolved against
Assembly-CSharp with and without the `TI` prefix and the `Template` suffix. It
falls back to a by-name sweep of every loaded assembly so a class added by a DLL mod
resolves too. Results are cached, misses included. Lookup keys off the exact class.
This is the 1:1 match for one template JSON file. A class whose entries all belong to
subclasses is retried with subclasses included.

Newtonsoft serializes one entry over the live object. Members pointing at other
templates collapse to a data name. Game states collapse to `{id, type, name}`. Unity
assets collapse to an asset name. `System.Type` collapses to a type name. This stops one
entry from dragging in the rest of the template graph. Reference loops are dropped.
Enums are written by name. A member whose getter throws is listed in the response's
`errors` instead of failing it. An entry that serializes past the response budget is
refused.

`query.enums` answers the question "what are the legal values of this template field".
A client cannot work this out from `query.template` alone. The serializer writes enums
by name. An entry never reveals the member set it was chosen from. It never reveals
whether a number a mod wrote is the same value under a different spelling. The verb
reads the member names and ordinals straight off the type with `GetRawConstantValue`.
It derives the field-to-enum map from `FieldInfo.FieldType`. It walks base classes so
the answer is one lookup rather than a chain. It reads fields only, never properties. A
`ReflectionTypeLoadException` from another DLL mod is caught. The unloadable types are
counted into `errors` rather than failing the verb. A partial table is always
distinguishable from a complete one.

The whole table is one response by design. It is roughly 69 KB against a 512 KB budget.
The verb does not split it, because a split lets a client pair an `enums` map from one
process with a `classes` map from another. The serialized string is cached per scope for
the process lifetime. The loaded assembly cannot change inside one.

Harmony is linked and called directly. `harmony.patches` enumerates every patched
method in the process, this mod's included.

## UI

Three verbs cover the screen, and you use them together. `ui.screenshot`
captures whatever is on it. `ui.view` chooses between the solar system and the
political map. `ui.screen` opens an info screen, the space object detail panel
or a rename panel. The bridge never sends synthetic input. So a panel with no
verb behind it cannot be captured, and so it cannot be tested. That gap is why
`ui.view` and `ui.screen` exist.

`ui.view` and `ui.screen` change UI state, and neither changes game state. Both need a
campaign, because `CanvasManager` builds its screen registry when the campaign
UI loads and holds nothing at the start screen. Both go through the engine's own
entry points (`ViewControl.GotoView`, `CanvasManager.ShowInfoScreen<T>`,
`HabDetailRequested`, `SpaceObjectDetailController.ViewSpaceObject`) and do not
reach into controllers. Each refuses the arms that another verb owns. `ui.view`
will not unload the campaign (`game.main_menu`) and will not enter or leave the
combat view (the combat verbs).

**Read the reply, and do not assume that the screen moved.** One of these paths is
synchronous and one is not. `ShowInfoScreen<T>` and `ViewSpaceObject` are direct
calls, and they are complete when the verb returns. `HabDetailRequested` is a
queueable event. So `EventManager` drains it from its own `Update` on a later
frame, and `ui.screen hab=<id>` answers `deferred: true` with the screen as it
stands now. Take the screenshot after a second call shows that the screen
changed. Do not take it after the first call.

The reverse holds for `detail`. The panel arrives inside the call. The info
screen that it displaces leaves a frame later, because `SetActiveInfoPanel`
raises `InfoPanelOpened` and `CanvasManager`'s listener for it is queueable. The
reply carries `infoScreenCloseQueued` and names the screen still standing. A
`rename` in that same frame goes to the detail panel for the same reason.

## Combat

Combat blocks the strategy clock. While any unresolved `TISpaceCombatState`
exists, or the precombat canvas is up, or an active-player prompt is queued, the
simulation tick stops advancing time. Every combat must be disposed of before a
run can continue.

A combat between two AI factions disposes of itself. The precombat listeners
answer their own stance prompts. The precombat interaction ends without the
screen ever being shown. The simulation callback writes the result back.
`combat.autoresolve` reports such a combat as resolving automatically and does
nothing.

A combat the active player is in stops and waits for the player. Resolving it
headlessly means taking the same route the precombat screen's own buttons take.
It takes one step per frame:

1. Wait for the combat to be promoted and picked up by the precombat controller.
2. Submit the player's stance through `PrecombatController.StanceSubmit`.
   Prefer Defend among the stances the combat allows. This runs the same
   player action the button runs and is synchronous.
3. Wait until both stances (and both bids, when the stance pair demands bidding)
   are in. Only AI factions can be outstanding here. The game's prompt handler
   serves AI factions only. The wait loop that runs after the precombat
   interaction ends never sees a human answer. An outstanding non-AI
   faction fails the verb, so the verb does not risk that loop.
4. `PrecombatController.AutoresolveSelected()` to end the precombat interaction.
   This starts the simulation coroutine.
5. Poll `autoresolving`. When it clears,
   `PrecombatController.OnAcceptAutoresolveSelected()` applies the result.
   It clears the blocking prompt, and ends the combat.
6. Applying the result raises the combat-ended event. This puts the post-combat
   report on the precombat canvas. The simulation tick returns early while that
   canvas is enabled. Leaving it up stops every later combat from being
   promoted and stops the clock. `PrecombatController.OnClosePostCombatButtonSelected()`
   closes it. This is the same call the human's close button makes. It also replays a
   combat that arrived while the report was up, which the controller defers.
   Time is not touched. The vanilla continue button pairs that close with
   `gameTime.Play()`. The bridge deliberately calls only the close. It leaves
   speed and pause to the client.

The work runs in the per-frame tick, never inside the verb. No step can hold
a frame. A step that throws disarms and leaves the reason in
`combat.status.autoresolve.error`. A resolution that stops making progress
disarms on a frame budget rather than staying armed.

### A combat that ends with nothing to accept

Steps 5 and 6 assume a simulation the player accepts. Not every combat produces
one, and two different engine paths take the combat away instead. When either
happens, the machine is in an earlier phase. It waits for something that will
not arrive, until the combat disappears from under it.

**In the first case, the combat was never promoted.** This case is the common
one, and the one a fixture-built fight hits. `combat.start` only caches its two
fleets and its hab. `TISpaceCombatState.StartCombatFromStrategyLayer` promotes
the combat a frame or more later. When the cached assets fail its gate, it
archives the combat, removes it from the `GameStateManager` and calls
`SpaceCombatManager.SetCombat(null)` instead. `InitializeCombat` never runs and
`Autoresolve` is never reached. The gate's clauses are on the `combat.status`
row above.

**In the second case, `Autoresolve` ended the combat outright.**
`TISpaceCombatState.Autoresolve` simulates when
`fleets[1]` or `hab` is non-null. Otherwise it calls its own local `EndCombat`,
which is `RecordSurvivors`, `EndCombatForStrategyGame` and
`SpaceCombatManager.SetCombat(null)` and nothing else. No `SimulatedCombat` is
ever set, `autoresolving` is never raised, and the combat is archived and gone.
That branch needs both fields null at once, and `InitializeCombat` is the only
writer of `fleets[1]`. So past a successful promotion, the branch means a
hab-only combat in which `HandlePrecombat` set `hab` to null: a defender that
evaded. A
two-fleet fight cannot get there.

`PromptBeginCombat` is the casualty. `PrecombatController.OnCombatInitiated`
queues it. Every engine path that removes it is one of that screen's own button
handlers: `OnAcceptAutoresolveSelected`, `CloseResolveSelected`,
`LiveResolveSelected`, `CancelAttackButton`, `OnRejectAutoresolveSelected`. None
of them runs on this path. The engine ignores an unhandled faction prompt in
silence and does not drop it. So a prompt left standing blocks saving and holds
the clock for the rest of the campaign.

So when the tick finds its combat gone with no canvas left to close, it removes
that prompt itself before it disarms. It uses the engine's own five-field
removal and says so in `combat.status.autoresolve.note`. The note survives the
disarm. The next arm clears it.

### Arming again after a failure

A failed tick disarms. So a client that polls for a combat sees one present and
nothing armed, and calls `combat.autoresolve` again. An arm re-enters the
machine at the start. This defeats the guards that steps 4 and 5 rest on. Those
steps advance the phase before they make a call that must not repeat, and an arm
resets the phase. A second `AutoresolveSelected` raises a second
`PrecombatComplete`. A second `OnAcceptAutoresolveSelected` reaches
`ApplySimulatedCombat`, which writes the same battle's damage into the real game
states.

So the machine keeps a record of what the last failure on a combat left behind,
and that record outlives the disarm. `combat.status.autoresolve` carries it:
`attemptedCombat`, `attempts`, `reached` (the furthest phase entered),
`errorKind`, `firedAutoresolveSelected`, `firedAcceptAutoresolve`, and
`retryable`.

The machine refuses to arm in five cases, and names the combat, the phase and
the error: `firedAutoresolveSelected`, `firedAcceptAutoresolve`, an `errorKind`
of `stable` (a failure no retry changes: a stance or bid owed by a second seated
faction, a controller whose active player is stale, a controller that lost the
combat), an `errorKind` of `deadend` (the stall was in the closing phase, so the
combat is archived with the canvas still up and no arm reaches it), and a second
attempt that recorded an error. The attempt count alone refuses nothing. For
example, a combat whose two sides both turn out to be AI disarms cleanly with a
note, and a second arm on it is harmless. Every other failure (no controller
yet, no active player yet) is worth the one retry that the budget allows.

`retryable` is that same decision, read and not made. One predicate answers
both, so the report cannot disagree with what the next arm does. It is answered
for the combat that the reply is about. When the reply is about no combat, it is
answered for the combat that `attemptedCombat` names. The reason is that the
record refuses arms on the combat it names and on no other.

The record is cleared when a different combat is armed, and by `saves.load`,
`campaign.new` and `game.main_menu`. Those three clear it because it names a
combat by id and `ClearAllGameStates` resets the id allocator. The next campaign
in this process hands out the same ids again. So a record left standing would
refuse the first arm of a fight that comes later.

After a refusal, look at `combat.precombat`. Start with `action=status`, which
reports whether the canvas is up and which buttons are live. It is not always a
way out. `AutoresolveSelected` ends the precombat interaction, and
`EndPrecombatInteraction` deactivates `preCombatUIObject` and hides the canvas.
So a dead end reached after step 4 can have no button left to press. Dropping
`PromptBeginCombat` is never the answer either, because the precombat canvas
also freezes the clock, and a drop of the prompt leaves that canvas up. The dead
ends reached before step 4 do have a live cancel button.

With `ai.control` engaged, `combat.autoresolve` refuses and does not report the
combat as resolving automatically (see its row). A client that wants a fight
flown by a human does not call `combat.autoresolve`. The combat stays pending,
and `combat.status` reports the block. The stance is `combat.stance` and the
begin-combat prompt is `combat.precombat`. See their rows.

## Campaign entry

`campaign.new` drives the start screen rather than assembling a scenario itself. The
menu controller already holds a live scenario built at scene start. It holds a faction
list, a difficulty dropdown, and a start button that reads all three. The verb sets
those controls and presses the button.

Order is fixed. It sets scenario, then the other options, then difficulty, then faction.
Choosing a scenario rebuilds the allowed-faction list and resets the faction dropdown.
That reset discards a faction set before it. A `FactionCouncils` option rebuilds that
list too. This is why every option is written before the faction is picked. Difficulty
is an index into the four start-screen levels. It is reported as the campaign's own 1-4
numbering. The campaign reads the dropdown directly at launch. The start button also
runs a default-options pass, and that pass restores everything else from the last
recorded difficulty rather than from the control. The tutorial toggle is forced off
through its own handler. It defaults on for a player's first ever game. The tutorial
gates the map behind scripted steps no client can answer.

An `options` entry is a meta template dataName. The template carries the category it
belongs to. The wire format is names alone. The verb writes each one where the
picker's dropdown writes it. An empty entry, a name matching no meta template, a
template that is not a new-campaign option, a category the scenario arg owns, and two
options in one category are each refused. The whole list is resolved before the
first option is written. A rejected list leaves the option map untouched. The
scenario arg is settled ahead of all of this. It stands whatever happens to the
options. `query.scenarios` lists every selectable option grouped by category.

Three of the menu's private members are read by reflection. A faction name is matched
against the allowed-faction list that its dropdown handler indexes. The start
options map is reported back as the categories the launch will read. If the scene
manager is absent, the menu never finished its own start. The controls the verb
sets and the methods it calls are public.

Launching reloads the scene. The verb returns the choices it made and leaves the
wait to the client, as `saves.load` does. It refuses while a campaign is loaded, when
the menu has not finished its own initialization, and while either the start screen's
or the load menu's loading screen is up. That last check is what stops a second launch.
A scene load takes tens of seconds and produces no campaign until it finishes. Every
other guard still passes. The loading screen each route raises is the only standing
record that one is already running.

## Prompts

A prompt in either of the active player's queues stops the simulation tick and pauses
time. Prompts belonging to other factions never block. The game's own prompt handler
answers prompts for AI factions only. So the player's queue accumulates.

`prompts.dismiss` takes two passes.

The screens pass repeats what the vanilla Autopilot does in a frame. This is the map of
every modal that can strand an unattended campaign. It handles the alert box (okay,
then close, then go-to, repeated while any is live, then the first live option button
on a notification that carries a choice). It handles the policy panel cancelled and
confirmed, the diplomatic response panel declined, an ally's war call declined, and a
faction greeting continued. It handles the diplomacy screen closed, an illegally-placed
army sent home, the research screen closed, and a trajectory change cancelled. Each is
guarded on its own so one failure does not stop the rest. The precombat screen is
deliberately absent. `combat.autoresolve` owns it and drives it a step per frame.

The prompt pass answers by name. It runs the same player action as the game's own AI
path. This includes a tech and a project chosen by the AI's selection strategies. It
includes councilor missions confirmed through the assignment screen's button. It
includes an unassigned org sold when the faction is over its org limit. Anything else
is reported as skipped with the reason.

**Only the screens pass answers a narrative event.** The prompt pass never selects an
option for one.

An event is two independent queue entries, the alert and the prompt. An answer
through the prompt queue would leave the alert box standing, and the box would
then apply the same choice a second time.

The alert box is also the only path that runs the notification-side teardown. The tail
of `OnOptionButtonPressed` clears `receivingInputForNarrativeHotkeys`, drops the
resource listener, calls `CleanUp` and resumes the clock. If the prompt pass meets a
narrative prompt before its box comes up, it reports the prompt as skipped and says so.
The screens pass takes it on a later call. A `type`-filtered call skips the screens pass
entirely, so it can never answer one.

The prompt pass does one thing to a narrative prompt, and that thing applies no option.
It drops a prompt that nothing can ever answer (`dropped: true`, with `deadEnd` saying
which case it was). Otherwise that prompt blocks the clock for the rest of the campaign.
Two cases qualify, and they are the engine's own condition from
`HandleRespondToNarrativeEvent`: no narrative event template behind the prompt, and the
event's target gone (null or deleted). The alert box tests for the second one.
`OnOptionButtonPressed` tests `currentNarrativeEvent.selectedTarget` for null and for
deleted. On either, it logs the target away and skips the `StartAction` that is the only
construction of `SelectNarrativeEventOption`. It runs its teardown in both cases. So the
press consumes the box, the box does not return, and nothing is left that can answer the
prompt. The drop runs whichever way `narrative` is set, because it applies no option and
so does not answer a story event. `narrative: false` is the mode that a caller is in
while it drives `alert.choose` by hand. That is how the campaign reaches this state in
the first place.

`alert.choose` reports the same thing from the other side, in its `answered` field,
which its verb row above spells out. The verb refuses a press when the option button is
live but the controller does not yet take narrative input. A delayed coroutine sets
`receivingInputForNarrativeHotkeys`, and the game discards a press ahead of it silently.

The rule that picks the button is the engine's own: `StratNarrativeResponseSelector`,
the class that `TIPromptQueueState`'s constructor installs. It weighs every valid option
by its `baseAIPreference` and the faction's AI values. When no option carries a weight,
it falls back to option 0 by itself. So a single-option acknowledgement answers 0 either
way. The range it walks is `numOptions`, not `eventOptions.Count`. Of the 260 shipped
events, 179 declare fewer options than that list holds (`event_Hurricane` is 2 against
4). The popup also builds its buttons from `numOptions`. If the strategy throws or
answers outside that range, or its pick is not a live button, the fallback is the first
live button. The engine derives the interactability of a button from
`NarrativeEventOption.ValidOption`, the same test the strategy filters on. Index 0 is
the exception, because the popup always offers it. `pickedBy` says which rule produced
it.

**The pass reports every narrative answer**, because an unattended run that answers story
events silently is worse than one that stops.

With `all`, `prompts.dismiss` then drops whatever is still queued, except a narrative
prompt. The decision behind a dropped prompt goes unmade. This costs a research slot or
a mission phase and leaves the save intact. It is the difference between a run that
continues and a run that sits paused forever.

A narrative event is the exception because it has no forfeit. The alert and the prompt
are independent queue entries. `AlertNarrativeEvent` is called once at trigger time.
Nothing on the prompt side reaches back into the notification queue. `RemovePrompt`
takes the prompt half. The box still arrives on schedule with its option buttons live,
so the choice is still applied, with its costs and grants. A drop of one hides a pending
decision and does not forfeit it. So `all` reports it under skipped and leaves it for
the box. To take the decision yourself, use `narrative: false` and `alert.choose`.

The pass reports a prompt under `forced` only when it actually left the two
lists that the clock counts. The measurement is `activePlayerNationPromptList`
and `activePlayerFactionPromptList`, not `RemovePrompt`'s return value.
`RemovePrompt` returns the MASTER list's result and discards the mirror's. It
touches the mirror only when the prompt's nation still has `executiveFaction ==
activePlayer`, or when it has no executive faction and the nation is gone. A
nation handed to a different, non-null faction meets neither, so the call
returns true with the entry still blocking. One that did not leave is reported
under `skipped` with `stillBlocking` and the reason, so `remaining` and this
pass cannot disagree. The annotation lands on the entry that belongs to that
prompt. The pass finds that entry by prompt identity and not by name. `Prompt`
is a struct with value equality over all five fields, and two nations can hold
the same prompt name at once.

The answer set covers three prompt types that the engine's own prompt handler does not
cover. The engine ignores an unhandled faction prompt in silence and does not drop it.
The three types are:

- **`PromptSelectSpaceCombatStance`**, queued by the precombat screen. The
  engine's handler serves it to AI factions only, so the active player's copy
  sits there and holds the clock. The answer is Defend, through
  `PrecombatController.StanceSubmit`. That is the screen's own button path and
  what the vanilla Autopilot submits. `SelectCombatStance.Execute` removes the
  prompt itself. The pass measures the answer against the active player's lists
  and does not assume it from the call. Three conditions must hold before the
  pass answers. If one fails, the pass skips the prompt and reports that
  condition as the reason. The conditions are: a live precombat controller with
  its canvas up, the autoresolve machine idle (armed, it submits the stance
  itself), and the screen showing the combat that this prompt belongs to. The
  last one is a real case. `SpaceCombatManager.CombatInit` queues the prompt
  with the new combat in `relatedGameState` whatever the screen is doing. But
  `PrecombatController.OnCombatInitiated` stashes the event in
  `delayedCombatInitiationEvent` and returns before `set_combat` whenever a
  post-combat report is still up, so the two diverge. In that case, a submit on
  the screen's combat would answer a different fight. This prompt would then go
  on blocking the clock, because `SelectCombatStance.Execute` removes the prompt
  keyed on its own combat. `combat.precombat action=close` closes the report,
  and the screen then takes the new combat. An answer to a stance also has a
  consequence one call later, on two conditions.
  `SpaceCombatManager.StanceSubmitted` returns at once unless
  `combatState.HaveStancesBeenSelected` is true. Then it queues
  `PromptSelectSpaceCombatBid` on the combat's factions only when
  `combatState.requiresBidding` is true. So a non-zero `remaining` straight
  after a successful answer is the bid. A `remaining` of zero is a combat that
  needs no bid. Neither is a failed answer. `combat.stance` is the same submit
  with a stance of the caller's choosing.
- **`PromptBeginCombat`**, queued by `PrecombatController.OnCombatInitiated`, has no
  entry in the answer table and cannot have one. There is no neutral answer to
  give it. Every button that clears it commits an outcome (close, cancel,
  reject, live). One of them is the accept that `combat.autoresolve` owns and
  fires exactly once. So the pass reports it as skipped, and `combat.precombat`
  is the contracted path. Every path off that screen removes it except
  `OnClosePostCombatButtonSelected`, which the autoresolve machine takes when
  the post-combat report is what is up. On the ordinary path this is invisible,
  because `OnAcceptAutoresolveSelected` already removed the prompt. On the path
  where the combat ended before simulation, it strands the prompt. The machine
  and `combat.precombat action=close` pair the removal with that button.
- **`PromptSelectTrajectory`**, queued by
  `OperationCanvasController.OpenThrustProfileTool` and removed by its private
  `CloseThrustProfileTool`. It records that a tool is open and forfeits no
  decision. The screens pass presses `changeTrajectoryCancelButton` when it is
  up. The answer pass adds the public `CloseActionPanel(true)`. That call
  reaches the same engine teardown for the ordinary-targeting case, where that
  button is not up. The pass drops the prompt directly only when neither path is
  on screen.

## Serialization rules

- Query verbs return curated, hand-built flat objects. Raw game objects are
  never fed to a general-purpose serializer. The state graph is cyclic and
  huge.
- Game-state references collapse to `{id, type, name}` everywhere. This includes
  inside `query.state`. The client walks the graph by issuing more queries.
- Newtonsoft (ships with the game) does the JSON encoding.

## Compatibility

Response fields can grow. Clients must tolerate unknown fields. All list responses carry
paging fields (`count`, `returned`, `truncated`) alongside the items.

The DLL is loaded into the game, so a rebuilt DLL reaches the bridge only on a
game restart. `version` reports which one is answering. A client's own staleness
is invisible on the wire and is the client's to report.
